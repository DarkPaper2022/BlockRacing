# 本机双客户端 E2E 与 Mock 边界

## 目标与入口

`./run-e2e.sh` 一次启动一套隔离的真实 Paper 服务端和两个真实 Fabric 客户端。运行目录为
`target/e2e-runtime`，世界会在后续运行中复用以减少区块生成开销；每次只清除该隔离运行时的
`game-progress.yml`。不会清理或复用 `/home/darkpaper/Game/blockracing-draftout` 的世界。

默认网络模型为每客户端 RTT 60 ms、抖动 5 ms、下行 3 MiB/s。两客户端拥有独立的 Minecraft
run directory 与 Xvfb display，避免 `session.lock` 和显示器冲突。完整日志写入
`target/e2e-logs/<timestamp>/`。

```bash
./run-e2e.sh

# 可覆盖 Paper 路径、端口或固定目标
BLOCKRACING_PAPER_JAR=/path/to/paper.jar \
BLOCKRACING_E2E_PORT=25575 \
BLOCKRACING_E2E_TARGETS=CHERRY_PLANKS,STONE,DIRT,COBBLESTONE \
./run-e2e.sh
```

单次运行覆盖：

1. 两客户端通过真实 54 格大厅菜单分别选择红/蓝队并准备；红方点击真实“开始”按钮。开局不以
   RTP 候选数为门槛；若完整候选尚未就绪，请求会抢占已有安全中心或走单中心快速生成，不等待
   625 区块后台任务。没有
   `/debug setteam` 或 `/debug start`。
2. 两端订阅真实 `board_request` / `board_v1` 数据，验证队伍、目标顺序、总分与胜利线。
3. 红方发送真实收藏 payload，并验证红方可见、蓝方不可见。
4. 两端在同一个墙钟时刻由客户端发送 `/give`，服务端仍通过正常库存轮询、共享互斥、计分、
   收藏清理和面板推送完成结算。脚本最后跨日志确认两队所得分之和恰好等于目标分。
5. 两方各执行一次免费 RTP；竞争目标的实际胜方再以刚获得的 2 分执行一次付费 RTP。使用真实
   传送包、本地区块可用和下一次世界渲染事件计算网络/区块/首帧耗时。

## Mock 边界

常规 E2E 唯一服务端测试缝是 JVM 属性 `blockracing.test.targets`：它只替换随机目标列表生成。CSV 加载、
目标定义、队伍、准备、开局门槛、库存/Goal 判定、互斥、分数、胜利线、收藏、RTP 和网络协议
全部运行生产实现。非法或不存在的目标会立即拒绝启动对局。

客户端暂时获得隔离测试服 OP，以便由客户端本人发出原版命令。OP 不是完成钩子；例如 `/give`
只改变库存，是否完成仍由插件每 5 tick 的生产轮询决定。测试没有 `setscore`、`skip`、直接字段
写入或测试专用“完成目标”命令。

R5 另用 `blockracing.test.rtp.target-pool-size` 将缓存容量设为 0/1，以确定性制造 cache miss；它只
改变缓存容量，不提供目的地、不完成传送，也不绕过 Paper 区块生成、找安全落点、扣分或传送协议。

## 目标类型完成器

`TaskCommandPlanner` 是客户端侧的命令计划层。当前稳定支持：

| requirement | 输入方式 | 完成仍由何处判断 |
| --- | --- | --- |
| 空（普通方块/物品） | `/give` | 团队库存轮询 |
| `item:` | 一个或多个 `/give` | Goal 物品条件 |
| `advancement:` | `/advancement grant ... only` | Advancement 进度刷新 |
| `effect:` | `/effect give` | Goal 效果条件 |
| `level:` | `/experience set ... levels` | Goal 等级条件 |
| `location:` | `/tp` / `/execute in` | Goal 位置条件 |

下列类型不能仅靠一条可靠指令完成，暂不计为 E2E 已覆盖：consume、breed/tame、玩家归因 kill、
break/craft/use-block、equipment、damage/death、钓鱼、望远镜、持续穿戴以及复合 unique/all/total。
后续应为每类实现客户端物品使用、方块交互、实体瞄准/攻击和容器点击动作；不得增加服务端
`completeTask` 一类捷径。命令规划器对这些类型显式返回 unsupported，避免假阳性。

## 开销设计

- Paper 世界跨运行复用；插件进度每轮清空。
- Maven/Gradle 先各构建一次；两个 `runClient` 复用产物并跳过 `classes`。
- 服务端堆 1–2 GiB，Gradle 单进程上限 768 MiB、最多两个 worker；两个客户端并行。
- GNU time 记录墙钟和直接启动作业的资源；另以独立 session/process group 为边界，每秒汇总一次
  整棵服务端或客户端进程树 RSS，写入 `*.group.resources`，避免只量到客户端启动脚本。
- RTP 全视距预生成是刻意保留的后台主要开销，但 cache miss 不再等待它完成；前台只生成安全
  中心区块并传送，周边区块随后按 Paper 的正常玩家视距加载。
- 一轮同时覆盖两队同步、并发 RTP、免费/付费路径和竞争结算；通常无需为每个断言重启游戏。

## 运行记录

### R1：双客户端真实大厅 + 单目标互斥 + RTP

- 目的：确认新的编排和低 Mock 边界可实际运行，并记录墙钟时间与峰值资源。
- 方法：默认配置，一服两客；固定四个目标；红 2 次、蓝 1 次 RTP。
- 结果（2026-09-29，日志 `target/e2e-logs/20260929-030827`）：通过。总墙钟约 2 分 55 秒；
  构建到服务端就绪约 21 秒，客户端启动/入服约 33 秒，6 个开局候选预生成约 84 秒，开局后
  场景约 33 秒。红蓝在同一秒发出命令，服务端仅为红方结算 2 分，蓝方 0 分。收藏在红方为
  true、蓝方为 false，结算后自动移除。蓝方免费 RTP 总耗时 150 ms；红方免费与付费 RTP
  分别为 162 ms、142 ms（注入 RTT 60 ms、抖动 5 ms、下行 3 MiB/s）。
- 发现并修复：并发 `xvfb-run -a` 选号竞态；首次启动无障碍页阻塞 TitleScreen 自动连接；网络
  抖动模拟曾让包乱序而产生旧面板快照覆盖新快照。现使用固定隔离 display、tick 级连接器，
  并按 TCP 语义维持每方向交付顺序。R1 后的代码审阅还发现 RTP 调度曾把“已经提交的最后一批
  异步区块”当作“已经生成”；现分别记录待调度、飞行中和已完成数，仅在飞行数归零后发布候选，
  并增加回归测试。该计数修复由单元测试验证，未倒填为 R1 的端到端覆盖结论。
- 结论：单轮已覆盖大厅、协议、队伍隔离、互斥计分、免费/付费 RTP；主要固定开销是两个
  Fabric 客户端约 33 秒，主要变量开销是保留的 RTP 全视距预生成。本轮尚未启用资源文件采样；
  后续运行会在同一日志目录生成 `server.resources`、`red.resources`、`blue.resources`（GNU time）。

### R2：修正后的 RTP 完成门槛

- 目的：确认候选只在全部异步区块完成后发布，并验证资源采样和精确进程组清理。
- 方法：默认一服两客配置；测试前因 Maven `clean` 清除了 `target`，因此本轮从空世界生成。
- 结果（2026-09-29，日志 `target/e2e-logs/20260929-031830`）：通过。服务端作业墙钟
  3 分 11 秒、峰值 RSS 2,505,332 KiB，运行目录 297 MiB。蓝方 RTP 117 ms；红方免费、付费
  RTP 分别为 213 ms、171 ms。互斥仍仅给红方 2 分，两个客户端均输出 PASS。
- 测量修正：客户端 GNU time 数据只覆盖其启动脚本，不能代表游戏 JVM；已增加进程组 RSS 汇总，
  将从 R3 起报告完整客户端进程树峰值。R2 已实际覆盖并通过修正后的 RTP 计数，不再只依赖单元测试。

### R3：复用世界 + 完整进程树开销

- 目的：复测同一真实链路，并用进程组采样获得两个客户端的完整峰值 RSS。
- 方法：复用 R2 世界，默认网络参数和四目标 fixture；每秒汇总各独立进程组内所有进程 RSS。
- 结果（2026-09-29，日志 `target/e2e-logs/20260929-032319`）：通过。服务端作业墙钟
  2 分 25 秒，进程组峰值 2,561,432 KiB；红、蓝客户端作业墙钟分别为 2 分 13 秒、
  2 分 11 秒，进程组峰值分别为 309,920 KiB、327,844 KiB。三组峰值简单相加约 3.05 GiB，
  但它们不保证发生在同一采样时刻。运行目录增至 410 MiB。蓝方 RTP 213 ms；红方免费、付费
  RTP 分别为 177 ms、188 ms；互斥、收藏隔离和两端 PASS 均再次成立。
- 结论：世界复用主要缩短服务端装载和出生区准备，随机远端的 6 候选全视距预生成仍是约
  80 秒的主要变量开销。当前本机内存峰值量级可接受，且一次运行同时覆盖两客户端竞争与三次 RTP。

### R4：取消 RTP 开局硬门槛

- 目的：验证候选不足不会阻止开局，缺失的初始传送会排队并自动完成。
- 方法：首次使用全新隔离世界 `target/e2e-runtime-no-start-gate`；后续复用该世界跑完整场景。
- 结果：首次运行（日志 `target/e2e-logs/20260929-115736`）在池中仅有 1 个候选时即进入
  `INGAME`，旧门槛对两人局为 6。红方立即完成初始传送，蓝方排队约 12 秒后自动传送，证明硬门槛
  和排队降级均已实际覆盖。该轮还发现普通 RTP 在池空时快速失败后，测试客户端不应固定等待包。
- 修正：普通 RTP 保持快速失败、不预扣积分；测试客户端每 15 秒像真实用户一样重试。考虑全视距
  新区块生成波动，单次 RTP 等待上限为 20 分钟。
- 完整复测（日志 `target/e2e-logs/20260929-120727`）：通过。开局时仍只有 1 个候选，红方排队约
  5 秒后完成初始传送；两端竞争、蓝方免费 RTP、红方免费与付费 RTP 全部 PASS。服务端作业墙钟
  1 分 46 秒；服务端、红、蓝进程组峰值分别为 2,773,900、253,148、244,140 KiB。
- 注：R4 记录的是当时的排队/快速失败策略，已由 R5 的前台快速降级策略取代。

### R5：缓存不足时前台单中心降级

- 目的：验证大缓存保留，但任何初始或用户 RTP 都不会因 cache miss 同步等待完整 625 区块任务。
- 零缓存方法：全新世界，`BLOCKRACING_E2E_RTP_POOL_SIZE=0`；修正客户端以“相对开局位置位移”
  判断初始 RTP，避免非零出生点造成假阳性。
- 零缓存结果（日志 `target/e2e-logs/20260929-133513`）：通过。开局池为 0，两个初始 RTP 和三次
  用户 RTP 全部走真实单中心生成；服务端单次安全中心准备 0.49–2.85 秒，未产生任何 625 区块
  READY 日志。两端初始 RTP 分别在开局同秒和约 3 秒后完成；三次用户侧总耗时分别为 0.74、
  1.15、5.66 秒，免费/付费路径均 PASS，无 15 秒重试。
- 压力缓存方法：另一个全新世界，缓存容量设为 1，要求同时覆盖完整候选和任务抢占。
- 压力缓存结果（日志 `target/e2e-logs/20260929-133129`）：通过。一个完整候选正常生成；池不足时
  初始 RTP 走单中心降级。后续两次 cache miss 分别抢占已完成 332/625 和 121/625 区块的后台
  候选，停止其余环调度并立即传送；三个用户 RTP 为 104/142/168 ms，两端均 PASS。被取消的
  candidate 5/6 没有随后进入 READY 池。
